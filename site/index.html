The launch clip: routing a request into a live session.

How a request moves

  1. 1

    request

    You send text, or one agent sends another session a task.

  2. 2

    route

    Jev when a key is configured, else a local BM25 matcher — no network call needed to pick the session.

  3. 3

    deliver

    A running session gets it in its inbox, injected at its next turn or tool call. An idle one is resumed headless.

  4. 4

    reply

    The answer lands back in the sender's inbox — or prints, when the send waited for it.

Session cards

Every session keeps a card — fifty words at most — saying what it is about, its state, and the next step. Routing and ls prefer the card over raw transcript text.

Agents write their own card; when they don't, a deterministic auto-card fills the gap — no LLM, no network.

Agents message agents

Sessions have inboxes. A message queued for a live session is injected at its next turn or right after its next tool call — the receiver answers with a reply to the same thread.

  • At most 3 hops back and forth, so two agents can't ping-pong forever.
  • everett event records what a session is doing: done, blocked, needs-input, info.
  • everett subscribe puts another session's events into your inbox.

Teach one, they all know

Parallel sessions drift apart. The shared core is the part they keep in common: everett learn pushes a fact, a nightly merge distills it, and every new session starts with the result.

push

everett learn "Atlas deploys from main" — capped, and secrets are rejected by a filter before anything is stored.

merge

everett trunk merge distills the inbox into a global core and a per-project core. A LaunchAgent can run it nightly.

pull

The SessionStart hook adds the global plus project core to each new session — local files only, silent on any error.

Ten MCP tools, one server

everett mcp is a stdio MCP server written with the standard library only — every MCP-capable harness gets Everett as native tools.

everett_ls
recent sessions with their cards
everett_route
pick the session a request continues
everett_send
route, then deliver a request or a reply
everett_inbox
messages waiting for your session
everett_card
write the calling session's card
everett_event
record done / blocked / needs-input / info
everett_subscribe
follow a session's or project's events
everett_learn
queue a fact for the shared core
everett_core
the shared core this project sees
everett_whoami
caller id, harness, and hop count

And the same verbs on the CLI: ls route send reply inbox event events subscribe cards learn core trunk dashboard gateway external doctor onboard

A dashboard that never leaves your machine

everett dashboard opens a read-only view of the same stores and cards: session filters, activity state, expandable cards, and copyable CLI actions.

It binds to 127.0.0.1 only, rejects foreign Host headers and write methods, and sends nothing anywhere.

Cloud agents, owner-bound

External agents — OpenAI dots, Grok Bot — register locally and reach Everett through a restricted MCP gateway with fixed identity, explicit destination lists, and authenticated loopback transport.

Local-first

Everett reads the stores your harnesses already write — every SQLite database is opened read-only — and keeps its own state under ~/.everett/. No harness session data is copied to a cloud service for ls, local routing, or inbox delivery. Optional Jev routing sends context to its API; the local matcher needs no network at all.

Accounts: coming

An Everett account would connect CLI installs across devices. The design is in progress — docs/auth.md.

Install

installer

curl -fsSL https://raw.githubusercontent.com/raitoxlol/everett/main/install.sh | sh

homebrew

brew tap raitoxlol/tap && brew install everett

cargo

cargo install --git https://github.com/raitoxlol/everett everett

then:

everett onboard && everett doctor

The Rust binary is the primary build — macOS arm64 and x86_64, Linux musl x86_64 and aarch64. The Python reference ships alongside it.

Named after Hugh Everett — every session branches from one origin but keeps its own history.
